# Monime checkout integration — how it works in this repo

This document explains, end to end, how AgrismartAPI integrates with Monime's hosted
checkout-session API (`POST /v1/checkout-sessions` at `https://api.monime.io`,
version `caph.2025-08-23`) and how the three checkout flows / reconciliation actually
work in this codebase. It reflects the real implementation — file paths, entity names,
and endpoints below all exist in this repo today.

Monime's own docs: https://docs.monime.io/apis/versions/caph-2025-08-23

## 1. What this integration does

- The **backend** creates a Monime "checkout session" for a signed-in buyer's cart,
  using credentials that live only on the server (`Monime` section of `appsettings.json`).
- Monime returns a **hosted checkout URL** (`redirectUrl`); the mobile app opens that
  URL so the customer can pay (card / bank / momo, including Orange Money).
- The mobile app **never sees Monime credentials** — only this backend holds them.
- Every create-session attempt (success, Monime-rejected, or network failure) is
  written to `CheckoutAuditLogs`; a successful session is persisted to
  `CheckoutSessions` so it can be looked up without calling Monime again.
- Because Monime's `checkout_session.*` webhook events are still listed as
  **"coming soon"** in Monime's own docs (not something to build against yet), this
  integration is **poll/admin-reconciliation based**, not webhook-based — see §7.

## 2. The three checkout paths

All three operate on the buyer's **current cart** (`/cart`) — the backend derives
line items/prices from the product catalogue server-side; it never trusts a
client-supplied price. Placing an order via any path empties the cart afterwards.

### Path 1 — Pay online (Orange Money, etc.) via Monime, with delivery

**`POST /checkout/sessions`** (Buyer only). Orange Money isn't a separate
integration — it's one of the mobile-money providers Monime routes to under the
`momo` payment option; it's simply what the customer picks on Monime's own hosted
page. Flow:

1. The backend places the underlying `Order` immediately (`PaymentMethod =
   MonimeOnline`, `PaymentStatus = Pending`, `OrderStatus = Pending`) from the
   cart's contents — this is what gets fulfilled/delivered once payment clears.
2. It calls Monime to create a **checkout session** for that order's line items,
   with `reference`/`callbackState` set to the order id (so reconciliation, and
   eventually a webhook, can be tied back to the right order).
3. It also calls Monime to create a **payment code** (`POST /v1/payment-codes`,
   same amount, `reference` = order id, `duration = "1h"`) — this is the real
   source of the USSD dial string (`ussdCode`, e.g. `*715*18284#`). **The numeric
   segment is generated by Monime per transaction — it is not a fixed merchant
   code.** This step is non-fatal: if it fails, the session/redirect flow still
   works, the response just comes back with `ussdCode: null`.
4. On success: a `CheckoutSession` row is persisted (carrying both the session's
   and the payment code's ids/status), the `Order` is linked to it
   (`Order.CheckoutSessionId`), the cart is cleared, and the mobile app can either
   open `redirectUrl` or tell the customer to dial `ussdCode`.
5. On failure of the checkout-session call itself: the order is deleted again (it
   only ever existed to give Monime a `reference`) and the cart is left untouched
   so the customer can retry.

**Correction from an earlier version of this doc:** it previously described a
static, configured `MerchantUssdCode` (e.g. hardcoded `*715*18284#`) as a fallback.
That was wrong — Monime has a dedicated **payment code** resource
(`https://docs.monime.io/apis/versions/caph-2025-08-23/payment-code/object.md`)
that generates a fresh `ussdCode` per transaction; there is no static/fixed
merchant USSD code. The `Monime:MerchantUssdCode` config key has been removed.

### Path 2 — Pay for the goods, collect them later (cash-on-pickup)

**`POST /cart/checkout`** or **`POST /orders`** with `"paymentMethod":
"cashOnPickup"`. No Monime session is created. The order is placed immediately
(`PaymentStatus = Pending`), held for the customer, and settled in person. An admin
**or the seller whose product is in the order** reconciles it afterwards via `POST
/checkout/reconciliation/transactions/{orderId}/confirm` then `.../paid` (see §7) —
money never moves through this backend or through Monime for this path.

### Path 3 — Place the order unpaid, held for 24 hours

Same endpoints as path 2, with `"paymentMethod": "unpaidHold"`. Functionally
identical at request time, except `Order.HoldExpiresAt` is set to `CreatedAt + 24h`.
A background hosted service (`Infrastructure/Orders/OrderHoldExpiryService.cs`, polls
every 15 minutes) automatically cancels (`OrderStatus.Cancelled`) any `unpaidHold`
order still `Pending`/unpaid once that window lapses. Paying before the window closes
(reconciled by an admin the same way as path 2) leaves the order alone.

All three paths converge on the same `Order` aggregate — what differs is
`PaymentMethod`, whether a `CheckoutSession` exists, and how `PaymentStatus`
eventually reaches `Paid`.

## 3. The Monime contract (verified against Monime's docs)

- Base URL: `https://api.monime.io`
- Create: `POST /v1/checkout-sessions`
- Retrieve (used for reconciliation, §7): `GET /v1/checkout-sessions/{id}`
- Required headers on every request:
  - `Authorization: Bearer {token}` — a space-scoped API token from the Monime dashboard.
  - `Monime-Space-Id: {spaceId}` — e.g. `spc-...`.
  - `Monime-Version: {version}` — pinned to `caph.2025-08-23` here. Don't leave it unset.
  - `Idempotency-Key: {guid}` — required on **create**, a fresh server-generated GUID
    per attempt (never reused across retries — see §8). Not needed on the GET.
  - `Content-Type: application/json` (create only).
- Every response — success or error — is wrapped the same way:
  ```json
  { "success": true, "messages": [], "result": { ... } }
  ```
  On error, `success` is `false`, `result` may be absent, and `messages` is a list of
  human-readable strings worth surfacing to the caller.
- Create-request body: `name`, `lineItems` (`name` + `price.currency`/`price.value`,
  where `value` is an **integer in whole minor units**, e.g. cents — never a float),
  plus optional `description`, `cancelUrl`, `successUrl`, `callbackState`,
  `reference`, `financialAccountId`, `paymentOptions` (per-method enable/disable for
  `card`/`bank`/`momo`/`wallet`), and a free-form `metadata` string map.
- `result.status` is one of exactly four values: **`pending`**, **`completed`**,
  **`cancelled`**, **`expired`**. There is no "failed"/"declined" status — a
  session that doesn't complete before `expireTime` moves to `expired`.
- A successful `result` also includes `id` (Monime's session id, e.g. `scs-...`),
  `redirectUrl` (open this), `expireTime` (sessions expire — Monime's default is
  ~1 hour), and echoes back most of what was sent.

### The payment-code contract (the actual USSD mechanism)

- Create: `POST /v1/payment-codes` · Retrieve: `GET /v1/payment-codes/{id}` ·
  Cancel: `DELETE /v1/payment-codes/{id}` (only while `status: "pending"`).
- Same envelope/header conventions as checkout sessions, including a required
  `Idempotency-Key` on create.
- Request body (as used here): `name`, `mode: "one_time"`, `amount.currency`/
  `amount.value` (minor units), `duration` (Go duration string — **Monime's own
  default is `"10m"`**, so this backend explicitly passes `"1h"` to roughly match a
  checkout session's ~1h expiry; leaving it at the default would let the USSD
  option expire long before the redirect page does), `reference`.
- `result.status` is one of five values: `pending`, `processing`, `completed`,
  `expired`, `cancelled`.
- **`result.ussdCode` is the actual per-transaction dial string** (e.g.
  `*715*18284#`) — Monime generates the numeric portion fresh for every payment
  code; it is never a fixed/static merchant code.

## 4. Architecture at a glance

```
Mobile app          AgrismartAPI                              Monime
  |                     |                                       |
  |  POST /checkout/    |                                       |
  |  sessions           |                                       |
  |-------------------->|                                       |
  |                     | Order.Create(..., MonimeOnline)        |
  |                     | (order placed, unpaid)                 |
  |                     |---------------------------------------->
  |                     |          POST /v1/checkout-sessions     |
  |                     |<----------------------------------------|
  |                     |---------------------------------------->
  |                     |          POST /v1/payment-codes         |  (non-fatal if this fails)
  |                     |<----------------------------------------|
  |                     | { success, messages, result } x2         |
  |                     | write CheckoutAuditLog (always, x2)      |
  |                     | write CheckoutSession (session + code)   |
  |                     | + link to Order; clear cart              |
  |<--------------------|                                       |
  |  { redirectUrl,     |                                       |
  |    ussdCode }       |                                       |
  |                     |                                       |
  | open redirectUrl OR dial ussdCode -> Monime collects payment -->
  |                     |                                       |
  |                     |  (later) admin/seller reconciles:      |
  |                     |  GET /v1/checkout-sessions/{id} ------->
  |                     |  GET /v1/payment-codes/{id} ----------->
  |                     |<----------------------------------------|
  |                     | Order.MarkAllSellersPaid() / CancelUnpaid() |
  |                     | + best-effort cancel the unused channel     |
```

## 5. Configuration

Credentials are **never** hardcoded in code and **never** accepted from the client —
they live in server config only (`Monime` section):

```json
"Monime": {
  "BaseUrl": "https://api.monime.io",
  "AuthorizationToken": "CHANGE_ME_monime_bearer_token",
  "SpaceId": "CHANGE_ME_monime_space_id",
  "Version": "caph.2025-08-23",
  "Currency": "SLE",
  "DefaultSuccessUrl": "https://agrismart.local/payment/success",
  "DefaultCancelUrl": "https://agrismart.local/payment/cancel"
}
```

Replace `AuthorizationToken`/`SpaceId` with real values from the Monime dashboard —
in production, set them via environment variables / a secret manager, not by
committing real values into `appsettings.json`. `Currency` must be a 3-letter ISO
code Monime supports for the merchant's space (Sierra Leone Leone `SLE` by
default). `DefaultSuccessUrl`/`DefaultCancelUrl` are used whenever the mobile app
doesn't send its own `successUrl`/`cancelUrl` in the create-session request.

## 6. Money handling

Unlike a naive integration that trusts client-supplied prices, `CheckoutAppService`
builds every Monime line item from the `Order` that was just created from the
**server-side cart** (`Application/Checkout/CheckoutAppService.cs` →
`OrderAppService.CreateMonimeOrderAsync`, which re-reads each product's current
price from the catalogue). A tampered client cannot change what it pays.

Amounts are converted to whole minor units (`ToMinorUnits`, `decimal * 100`,
rounded) since Monime requires integers — this assumes a 2-decimal-place currency
(true for `SLE`); revisit the multiplier if the configured `Currency` uses a
different number of minor-unit digits.

## 7. Reconciliation (no stable webhook yet)

Monime's `checkout_session.completed` / `.expired` / `.cancelled` webhook events are
marked **"coming soon"** in Monime's own docs as of this integration — there is no
documented signing scheme or stable payload for them yet, so this backend does not
implement a webhook receiver. Instead:

Reconciliation is **per seller**, not per order, because an order can span multiple
sellers (a multi-vendor cart checks out as one `Order`). `Order.SellerPayments`
holds one `SellerPayment` row per distinct seller among `Order.Items`; every
reconciliation action reads/writes exactly one of those rows. `Order.PaymentStatus`
is a derived aggregate recomputed on every change (`Paid` only once every seller's
row is `Paid`, `Pending` if any row still is, else `Confirmed`) — it's what the
buyer's own `OrderDto` shows, but it is **not** what a reconciliation action targets.

All of the following are callable by an **Admin** (any seller's row on any order) or
a **Seller** (only their own row, only on orders containing at least one of their
own products — same order-level scoping as `GET /orders/mine-as-seller`; enforced in
`CheckoutAppService.ResolveTargetSellerIdAsync`/`ResolveSellerScopeAsync`, `403`
otherwise). A Seller can never act on another seller's row, even within the same
order — the `sellerId` a Seller might pass is ignored outright and their own is
always used instead.

- **`POST /checkout/reconciliation/transactions/{orderId}/confirm?sellerId=`** and
  **`.../paid`** — the cash-on-pickup / unpaid-hold equivalent: the caller confirms
  receipt, then marks **their own seller row** fully paid/reconciled
  (`SellerPayment.PaymentStatus`: `Pending` → `Confirmed` → `Paid`), via
  `Order.ConfirmSellerPayment`/`Order.MarkSellerPaid`. `sellerId` is required from
  an Admin when the order has products from more than one seller (optional/ignored
  otherwise); a Seller's own seller id is always substituted regardless of what (if
  anything) is sent. Who did it is recorded on that seller's row
  (`SellerPayment.ConfirmedByUserId`/`ReconciledByUserId`).
- **`POST /checkout/reconciliation/transactions/{orderId}/sync`** — calls
  `GET /v1/checkout-sessions/{id}` **and**, if one was created, `GET
  /v1/payment-codes/{id}` (the customer may have paid via either the hosted
  redirect or the dialled USSD code), updates the stored statuses, and reconciles
  the order: either one reporting `completed` → `Order.MarkAllSellersPaid()` (and
  best-effort cancels whichever channel is still open, so it can't be used for a
  second payment); both dead (`cancelled`/`expired`) → `Order.CancelUnpaid()`. This
  marks **every** seller's row on the order paid at once — deliberately, since
  Monime collected one lump sum for the whole cart, so it's an external fact about
  the order as a whole, not one seller reconciling another's products. Use this to
  manually check on an order stuck at `Pending`, or wire it into a scheduled job
  once Monime's webhook is stable.
- **`GET /checkout/reconciliation/transactions`** — the reconciliation grid: every
  order the caller can see, with the order-wide `paymentMethod`/`paymentStatus`
  plus a `sellerPayments` breakdown — full for an Admin, restricted to just the
  caller's own row for a Seller (see README.admin.md for the full shape). The
  `paymentStatus` query filter is matched against the caller's own row for a
  Seller, not the order aggregate.

`GET /checkout/reconciliation/sessions[/{id}]` (the raw Monime session/audit
detail — see §8) stays **Admin-only** — it isn't seller-scoped and spans every order
on the platform.

**Follow-up once Monime's webhook is stable:** add a receiver that verifies Monime's
signature, looks up `CheckoutSession` by `MonimeSessionId`, and calls the same
`SyncMonimeSessionAsync` logic — it's already idempotent (re-running it against an
already-`Paid` order is a no-op via `Order.MarkAllSellersPaid`'s guard).

## 8. Idempotency & auditing

- **Idempotency key is generated server-side, fresh, per create-session attempt** —
  this endpoint is *not* idempotent from the client's point of view. Calling it
  twice creates two Monime sessions (and, since each call also places an order,
  two orders — the client should disable the checkout button while a request is
  in flight rather than relying on backend dedup).
- **Every create-session attempt is audited** in `CheckoutAuditLogs`, success or
  failure, including network failures where Monime was never reached
  (`ResponseStatusCode = null`). This is what makes "why did this customer's
  payment session fail to even get created" answerable without re-deriving it from
  application logs.
- **`CheckoutAuditLogs` and `CheckoutSessions` are separate tables.** The audit log
  always gets a row; the session table only gets one on success. A failed attempt
  has no `CheckoutSessionId`.
- **HTTP status mapping:** Monime 4xx → this API's `400` (the caller's input was bad
  — invalid currency, disabled account, etc.); anything else, including no response
  at all → `502` (the payment provider, not the caller, was the problem). See
  `CheckoutController`/`CheckoutReconciliationController`'s `catch (MonimeApiException ex)`.
- **Fields Monime might reshape** (raw session payload) are stored as a verbatim
  JSON text column (`CheckoutSession.RawResponseJson`) rather than modeled
  strictly, refreshed on every `sync` call — schema drift on Monime's side won't
  break ingestion.

## 9. Known limitations / follow-ups

- **No webhook receiver** — see §7; Monime's own docs mark checkout-session events
  as not yet available. Reconciliation today is admin/seller-triggered (`.../sync`)
  or, for cash flows, confirmed by hand by an admin or the seller who owns that
  product.
- **Pre-existing orders have no per-seller breakdown.** `Order.SellerPayments` was
  introduced after orders already existed in the database; the migration backfills
  it as an empty list for those rows rather than reverse-engineering a breakdown
  from `Order.Items`. Reconciling one of these legacy orders returns "seller has no
  products in this order" until/unless a data migration backfills real
  `SellerPayment` rows for them — new orders are unaffected.
- **`GET /v1/checkout-sessions` (list) isn't wired up.** Monime exposes a list
  endpoint; this backend only ever fetches sessions it already knows the id for
  (via `GetSessionAsync`), since every session here originates from an order this
  backend created. Add it if you need to reconcile sessions this backend lost track
  of.
- **Currency minor-unit assumption.** `ToMinorUnits` assumes 2 decimal places
  (matches `SLE`). If `Monime:Currency` is ever changed to a currency with a
  different minor-unit exponent, update the conversion in
  `CheckoutAppService.ToMinorUnits`.
- **The Monime-path order is a "staging" write.** If the checkout-session call
  fails, the order that was created to give Monime a `reference` is deleted again
  (§2, path 1, step 5) rather than kept around for a "retry this session" flow —
  there is currently no "resume checkout" endpoint; a failed attempt just means the
  customer taps checkout again from their (still-intact) cart.
- **Payment-code cancellation is best-effort only.** Monime only allows deleting a
  payment code while it's still `pending`/unused (same restriction on deleting a
  checkout session while `pending`), so once reconciliation tries to close out the
  channel the customer *didn't* use, that call can legitimately fail (e.g. the
  customer already dialled the code and it's `processing`). `CheckoutAppService`
  swallows that failure — it's cleanup, not a correctness requirement, since the
  order is already `Paid` by that point.
